## Architectural Decisions

### 1. `DeadMessageHandler` returns `CompletionStage<Void>` — must complete normally

```java
public interface DeadMessageHandler {
    CompletionStage<Void> handle(DeadMessageContext context);
}
```

Implementations must complete normally; they must not complete exceptionally. This contract protects against a handler failure masking the original publication cause. The async stage return allows handler implementations to perform non-blocking I/O (e.g., write to a Kafka DLQ, call an external alerting API) without blocking the calling thread.

**Why not `void`?** A void return would force any non-blocking handler to fire-and-forget with no backpressure signal. The `CompletionStage<Void>` return lets the dispatcher sequence the final failure acknowledgement — `markFailed`, then `handle`, then `completeExceptionally` — correctly even for async handlers.

### 2. Async STOP path uses `.handle().thenCompose()` to absorb handler exceptions

```java
return deadMessageHandler.handle(deadContext(message, attempt, pubEx))
        .handle((ignored, handlerEx) -> (Void) null)
        .thenCompose(ignored -> CompletableFuture.failedFuture(pubEx));
```

`.handle()` absorbs any exception from a misbehaving handler before `.thenCompose()` re-fails with the original `pubEx`. This preserves the contract that `dispatch()` always fails with the original publication cause, regardless of handler behavior.

### 3. Sync STOP path fires the handler as a side-effect and rethrows

```java
callMarkFailed(message, immediate);
deadMessageHandler.handle(deadContext(message, attempt, immediate)); // fire-and-forget
throw immediate;
```

The sync path (when `publisher.publish()` throws synchronously) preserves the existing test contract: `dispatch()` throws immediately. The handler is invoked fire-and-forget; its `CompletionStage` result is not awaited. This is intentional — the sync throw is the primary signal; the handler is a diagnostic side-effect.

### 4. `Instant.now()` used directly for `DeadMessageContext.failedAt`

`TimeProvider` injection is the platform convention. However, injecting a `TimeProvider` into the dispatcher solely for the `failedAt` diagnostic timestamp would require a 7th constructor parameter and complicate wiring. `DeadMessageContext.failedAt` is a diagnostic field (for logging and dead-letter context), not a business timestamp. `Instant.now()` is acceptable here and documented explicitly.

### 5. `LoggingDeadMessageHandler` as the default implementation

The 5-arg constructor (without `deadMessageHandler`) chains to the 6-arg primary with `new LoggingDeadMessageHandler()` as the default. The 3-arg and 2-arg constructors chain upward through the 5-arg. All existing callers using short constructors automatically gain the logging behavior with no code changes.

## Implementation Notes

### Constructor chain (6 → 5 → 3 → 2 args)

```
6-arg primary:   (publisher, outboxRepository, retryPolicy, backoffStrategy, retryScheduler, deadMessageHandler)
5-arg:           chains to 6-arg with new LoggingDeadMessageHandler()
3-arg:           chains to 5-arg with attempt→ZERO backoff and inline anonymous RetryScheduler
2-arg:           chains to 3-arg with new SimpleRetryPolicy(1)
```

### Java generic method — anonymous class required in convenience constructor

`RetryScheduler.schedule` is a generic method (`<T>`). Java cannot represent a generic method as a lambda (no single type erasure satisfies the descriptor). The 3-arg convenience constructor uses an anonymous class:

```java
new RetryScheduler() {
    @Override
    public <T> CompletionStage<T> schedule(
            final Supplier<CompletionStage<T>> action,
            final BackoffDelay delay) {
        return action.get();
    }
}
```

This is a language constraint, not a design flaw.

### Mockito strict-stubbing fix

`DispatchOutboxMessageServiceTest.handler_not_invoked_during_retries` originally declared a `lenient()` stub on `backoffStrategy.nextDelay()`. Under `MockitoExtension` default strict mode this was flagged as `UnnecessaryStubbing` because the service was constructed with the mock `backoffStrategy` but the stub was not invoked in that particular call chain. The fix replaced the mock with a lambda (`attempt -> BackoffDelay.ZERO`) passed directly to the 6-arg constructor, eliminating the stub entirely.

## Tradeoffs

- The fire-and-forget behavior of the sync STOP path means the handler's async work is not awaited when `publisher.publish()` throws synchronously. This preserves backward-compatible test behavior at the cost of a potential ordering gap. In practice, synchronous throws from the publisher are rare (routing/config errors), and the handler is invoked immediately as a side-effect.
- `DeadMessageContext` is a `record`, making it immutable and easy to test. The `cause` field is a `Throwable` reference — it carries the original exception chain rather than a serialized message, which is appropriate for an in-process handler but means the context is not directly serializable to Kafka or a database without a marshalling step.
- `LoggingDeadMessageHandler` always completes normally. A future handler that writes to a Kafka DLQ must also complete normally (absorb its own failures), per the `DeadMessageHandler` contract. This is documented in the interface Javadoc.

## Open Questions

- `Instant.now()` in `DispatchOutboxMessageService.deadContext()` — acceptable for a diagnostic timestamp; would need `TimeProvider` injection if exact reproducibility in tests becomes a requirement.

## Follow-ups

- **DLQ handler:** A `KafkaDlqDeadMessageHandler` that publishes permanently failed messages to a dead-letter topic is the natural next extension. It must implement the `DeadMessageHandler` contract (complete normally) and be gated on Kafka presence.
- **RetryAutoConfiguration:** Wire `ExponentialBackoffStrategy`, `ScheduledRetryScheduler`, `LoggingDeadMessageHandler`, and the updated `DispatchOutboxMessageService` as Spring `@Bean`s with configurable properties — deferred to a follow-up task.
- **Persistent dead-letter store:** A repository-backed handler that records permanently failed messages for replay tooling — a future operational capability.
