## Summary

Added structured lifecycle logging to `DispatchOutboxMessageService` covering all significant dispatcher transitions: dispatch started, dispatch succeeded, retry scheduled, and retry attempts exhausted. Every log entry includes `eventId`, `aggregateType`, `aggregateId`, `eventType`, and `correlationId` (from the `OutboxEvent` field; rendered as `-` when absent). No MDC is used in async callbacks because MDC is thread-local and the dispatcher executes across completion threads. The `LoggingDeadMessageHandler` ERROR log continues to cover the permanent-failure case — the dispatcher's WARN covers the dispatch-lifecycle view; together they are complementary, not duplicated.

## Architectural Decisions

### 1. Log message parameters instead of MDC in async callbacks

MDC is thread-local. The dispatcher uses `CompletionStage` callbacks (`thenRun`, `exceptionallyCompose`) that may execute on any thread pool thread. Pushing fields to MDC inside these callbacks would produce inconsistent results: the MDC entry would be lost if the callback runs on a thread that was reused from a pool with a different request context.

The correct approach: embed all contextual fields directly in the SLF4J message parameters. The log aggregator (Loki, Splunk, etc.) can then parse the structured `key=value` pairs regardless of which thread emitted the log.

### 2. Only `dispatch()` entry is synchronous — eligible for MDC

`dispatch()` is called synchronously by the outbox poller, making it eligible for MDC. However, the outbox poller runs on a background scheduler thread, not on an HTTP-request thread, so no HTTP-scoped MDC (correlation ID, request ID) is present at dispatch time. Adding MDC in `dispatch()` and removing it in a `whenComplete` handler would add complexity with no benefit. Plain message parameters are sufficient and consistent.

### 3. `corr()` helper renders null correlationId as `-`

`OutboxEvent.correlationId()` is nullable (events produced without a business correlation context will have `null`). SLF4J renders `null` as the literal string `"null"` in message parameters, which is confusable with the string `"null"`. The private `corr()` helper returns `"-"` for null, producing clearly intentional output in logs.

### 4. "Retry exhausted" at WARN; dead-message details at ERROR via `LoggingDeadMessageHandler`

The task requires exactly one log for "dead message delegated." `LoggingDeadMessageHandler` already logs at ERROR with full context including the cause. The dispatcher logs at WARN at the STOP decision point — a different severity indicating "this message used its full retry budget." These two log entries serve different purposes:

| Log entry | Severity | Emitter | Purpose |
|---|---|---|---|
| `Outbox message retry attempts exhausted` | WARN | Dispatcher | Dispatch-lifecycle signal; retry budget consumed |
| `Outbox message permanently failed after N attempt(s)` | ERROR | `LoggingDeadMessageHandler` | Operational alert; cause included; needs operator attention |

The two entries share `eventId` which ties them together in a log aggregator.

### 5. Success log chained after `markPublished`

```java
.thenRun(() -> outboxRepository.markPublished(message.eventId()))
.thenRun(() -> log.debug("Outbox message dispatched — ..."))
```

The success log is chained after `markPublished` so it only fires when the status update succeeds. A DB failure in `markPublished` skips the success log and completes the stage exceptionally — which is the correct observable behavior.

## Tradeoffs

- No log for "retry policy evaluated" at the individual-attempt level inside `attemptDispatch`. This keeps the log volume proportional: one DEBUG per dispatch start, one per retry, one WARN per final failure. Adding per-attempt "publish attempted" logs would double the noise for multi-retry scenarios.
- `delay.value().toMillis()` is used instead of `delay.value()` for the retry-scheduled log. Milliseconds are more readable than an ISO-8601 duration for short delays.
- No MDC push/pop in `dispatch()` even though it is synchronous. The cost/benefit does not justify it: the background poller thread has no HTTP-request MDC context, so the only MDC field we could add from the event is `correlationId` — but it is already embedded in the log message, making MDC redundant.

## Follow-ups

- **MDC in poller:** If the outbox poller is enhanced to propagate the event's `correlationId` into MDC for its duration, the dispatcher log entries will automatically inherit it. This would be done in the poller layer, not the dispatcher.
- **Metrics:** `dispatch.started`, `dispatch.succeeded`, `retry.scheduled`, `retry.exhausted` counters are the natural next slice, wired via Micrometer without touching the dispatcher log calls.
