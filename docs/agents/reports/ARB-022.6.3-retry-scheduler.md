## Architectural Decisions

### 1. `RetryScheduler` uses a generic method signature `<T>`

```java
<T> CompletionStage<T> schedule(Supplier<CompletionStage<T>> action, BackoffDelay delay);
```

The generic signature preserves full type safety at call sites and keeps the interface transport-neutral. The dispatcher calls it with `Supplier<CompletionStage<Void>>` internally; a future caller could use any type `T`.

**Implementation note:** Java does not allow a generic method to be represented as a lambda (generic methods have no single erasure that satisfies the lambda descriptor). The convenience constructors that inline a "execute immediately" scheduler use anonymous class syntax rather than a lambda expression. This is a language constraint, not a design flaw.

### 2. Zero-delay fast path avoids the executor entirely

When `delay.isImmediate()`, `ScheduledRetryScheduler` calls `action.get()` inline and returns its stage directly without touching `ScheduledExecutorService`. This matters for `SimpleRetryPolicy(1)` (no retry) and the 2-arg convenience constructor — neither ever reaches the executor, so there is no need to provide a real executor in those configurations.

### 3. `CompletableFuture` bridge for delayed execution

For non-zero delays, a `CompletableFuture<T> bridge` is created before submitting to the executor. When the scheduled `Runnable` fires, it calls `action.get()`, attaches a `whenComplete` handler that populates the bridge, and catches synchronous exceptions with a try/catch. This fully decouples the scheduler's return value from the executor's scheduling lifecycle.

### 4. Dispatcher constructor chain — 5-arg primary, 3-arg and 2-arg convenience

| Constructor | Suitable for |
|---|---|
| `(publisher, outbox, policy, backoff, scheduler)` | Production wiring with full retry + delay + scheduling |
| `(publisher, outbox, policy)` | Tests or configs that inject a custom `RetryPolicy` but want no delay between retries |
| `(publisher, outbox)` | No-retry path; defaults to `SimpleRetryPolicy(1)` |

All convenience constructors chain upward to the 5-arg primary. No behavior changes for callers using the 2-arg or 3-arg forms.

### 5. `BackoffStrategy.nextDelay` receives the *next* attempt number

When attempt `N` fails and the policy says RETRY, the dispatcher calls `backoffStrategy.nextDelay(N + 1)` — the delay before attempt `N+1`. This matches `ExponentialBackoffStrategy`'s convention that `attempt=1` returns `ZERO` and `attempt=2` returns `initialDelay`.

## Implementation Notes

The only non-obvious compile issue encountered: Java rejects a lambda as an implementation of `RetryScheduler` because `schedule` is a generic method. The convenience constructor uses an explicit anonymous class. This is documented in the Javadoc of `DispatchOutboxMessageService`.

## Tradeoffs

- The `ScheduledExecutorService` is injected, not created internally. Ownership of the executor lifecycle (shutdown, thread count) is the caller's responsibility. This is consistent with Spring's `ThreadPoolTaskScheduler` model and keeps the scheduler testable without managing real thread pools.
- Jitter is not implemented in this slice. The `BackoffStrategy` interface accommodates a jitter-aware wrapper in a future task without changing the scheduler.
- The `bridge` pattern (create `CompletableFuture`, populate in `whenComplete`) adds a thin indirection layer for delayed execution. The alternative — returning the `ScheduledFuture` directly — would expose executor-specific types to callers and lose the ability to chain standard `CompletionStage` combinators.

## Follow-ups

- **Auto-configuration:** A dedicated `@Bean` for `ScheduledRetryScheduler` and `ExponentialBackoffStrategy` wired into `DispatchOutboxMessageService` belongs in `OutboxSchedulingAutoConfiguration` or a new `RetryAutoConfiguration` — deferred to a follow-up task.
- **Jitter:** A `JitteredBackoffStrategy` wrapper (or jitter parameter on `ExponentialBackoffStrategy`) should be added before this reaches production traffic.
- **Dead message handling:** Once the retry pipeline is integrated with a real `ScheduledExecutorService`, events that exhaust all attempts need a durable dead-message path (DLQ, Kafka retry topic, or manual replay).
