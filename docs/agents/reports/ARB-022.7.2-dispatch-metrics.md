## Summary

Introduced a `DispatchMetricsRecorder` port in `platform.messaging.outbox.application` that defines the four lifecycle events the dispatcher emits: `recordStarted`, `recordSucceeded`, `recordRetry`, and `recordDead`. `MicrometerDispatchMetricsRecorder` translates these events into five counters and one timer. `NoOpDispatchMetricsRecorder` is the no-arg default, preserving backward compatibility for all existing constructors. `DispatchOutboxMessageService` threads `startNanos` (captured at `dispatch()` entry) through `attemptDispatch` and `handleRetryOrStop` so the end-to-end latency timer covers the full lifecycle including retries.

## Metric Catalogue

### Counters — all tagged `aggregateType`, `eventType`

| Metric name | When incremented |
|---|---|
| `messaging.dispatch.started` | `dispatch()` entry — first attempt only |
| `messaging.dispatch.succeeded` | After `markPublished` succeeds |
| `messaging.dispatch.retry` | Each retry scheduled (one per retry attempt) |
| `messaging.dispatch.failed` | Terminal STOP decision (permanent failure) |
| `messaging.dispatch.dead` | Dead-message handler invoked |

`messaging.dispatch.failed` and `messaging.dispatch.dead` are always incremented together on the STOP path; they are separate counters to allow independent querying (e.g., a future handler that silently drops rather than dead-letters would only increment `failed`).

### Timer — tagged `aggregateType`, `eventType`, `outcome`

| Metric name | Outcome tag values | Measures |
|---|---|---|
| `messaging.dispatch.duration` | `success`, `dead` | Wall-clock time from first attempt to terminal outcome (includes retries and scheduler delays) |

### Excluded high-cardinality tags

`eventId`, `aggregateId`, `correlationId`, `requestId` — excluded per task specification.

## Architectural Decisions

### 1. `DispatchMetricsRecorder` as a port, not direct `MeterRegistry` injection

Injecting `MeterRegistry` directly into the dispatcher would couple the dispatcher to the Micrometer API, requiring Micrometer on the test classpath for all dispatcher tests. A port interface keeps the two concerns independent: the dispatcher calls semantically named methods; the recorder translates to Micrometer. Existing tests use Mockito to stub the recorder with zero Micrometer knowledge.

### 2. `NoOpDispatchMetricsRecorder.INSTANCE` as the default for backward-compatible constructors

All constructors from 2-arg through 6-arg default to `NoOpDispatchMetricsRecorder.INSTANCE`. No existing call site is affected. The 7-arg primary constructor accepts an explicit `DispatchMetricsRecorder`.

### 3. `startNanos` threaded through private methods

The timer requires the start time from `dispatch()` to be accessible in the terminal-state callbacks (`thenRun` for success, `thenCompose` inside `handleRetryOrStop` for dead). Rather than capturing a mutable reference, `startNanos` is passed as a `final long` parameter through `attemptDispatch(message, attempt, startNanos)` and `handleRetryOrStop(message, attempt, failure, startNanos)`. This is thread-safe (primitive, effectively final in lambdas) and avoids any shared mutable state.

### 4. `recordDead` fires inside `thenCompose` after the handler stage

```java
.thenCompose(ignored -> {
    metricsRecorder.recordDead(message, attempt,
            Duration.ofNanos(System.nanoTime() - startNanos));
    return CompletableFuture.<Void>failedFuture(failure);
});
```

Placing `recordDead` here ensures the metric is recorded after the `DeadMessageHandler` completes (consistent ordering) and before the dispatch stage fails. Placing it before `.handle()` would record the metric even if the handler itself failed.

### 5. `micrometer-core` as an `optional` platform dependency

Micrometer is already adopted by all service modules via `spring-boot-starter-actuator`. Adding it as `optional` to the platform pom means it is on the platform's own compile/test classpath but is not propagated as a transitive dependency to platform consumers. Service modules already have it via actuator; the `optional` flag prevents a double-declaration risk for consumers that don't need actuator.

## Tradeoffs

- `recordDead` increments both `failed` and `dead` counters simultaneously. A future handler that re-routes permanently failed messages to a Kafka retry topic would still increment both — the distinction between "final failure" and "dead-lettered" would need a tag or a separate path at that point. For the current `LoggingDeadMessageHandler`, the two counters always move together.
- The timer captures wall-clock time including scheduler delays (the retry delay itself). This makes the timer a measure of "time to outcome from the operator's perspective" rather than "net transport time." For high-delay retry configurations (e.g., 30s backoff × 3 retries), the timer will show values in the minutes range. This is intentional and useful for alerting on SLA breaches.
- `System.nanoTime()` is used for elapsed measurement — appropriate for duration measurement, not absolute timestamps. `Instant.now()` is reserved for the `DeadMessageContext.failedAt` diagnostic timestamp.
