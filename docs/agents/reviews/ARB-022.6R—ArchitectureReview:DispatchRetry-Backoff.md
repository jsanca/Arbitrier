# ARB-022.6R — Architecture Review: Dispatch Retry & Backoff

Status: Done
Owner: Deep
Role: Architecture Review
Time spent: ~35 min

## Executive Summary

The retry subsystem is architecturally sound. The four-port abstraction (`RetryPolicy`, `BackoffStrategy`, `RetryScheduler`, `DeadMessageHandler`) cleanly separates retry-decision, delay-calculation, scheduling, and terminal-failure concerns. Every type is transport-agnostic — zero imports from Kafka, RabbitMQ, HTTP, or gRPC. The subsystem is ready for Kafka integration with two targeted improvements: fix the sync/async code-path inconsistency in the dispatcher and ship auto-configuration to wire the production pipeline.

## Strengths

### 1. Port-level separation with zero coupling

The four ports have no compile-time relationship. `RetryPolicy.evaluate` answers *should we retry?*, `BackoffStrategy.nextDelay` answers *how long to wait?*, `RetryScheduler.schedule` answers *when to submit?*, and `DeadMessageHandler.handle` answers *what to do when dead?*. This layered design is the subsystem's strongest decision — each port can be replaced, composed, or tested in isolation.

### 2. `CompletionStage`-native, non-blocking by design

Every interface returns `CompletionStage` — no `Thread.sleep()`, no `get()` / `join()` inside the pipeline. `ScheduledRetryScheduler` delegates to `ScheduledExecutorService` without blocking. This is correct for virtual-thread environments where blocking the carrier would stall all co-scheduled work.

### 3. Zero-delay fast path avoids executor overhead

`ScheduledRetryScheduler` bypasses the executor entirely when `delay.isImmediate()`. Under `SimpleRetryPolicy(1)` (no retry, the current production default) the executor is never touched. This keeps the common path allocation-free at the scheduler boundary.

### 4. Dead-message handler contract protects the publication cause

The `DeadMessageHandler.handle` contract — *must complete normally, must not complete exceptionally* — prevents a misbehaving handler from masking the original Kafka error. The dispatcher absorbs handler exceptions via `.handle((ignored, handlerEx) -> (Void) null)` before re-failing with the original `pubEx`. This is a subtle but critical correctness guarantee.

### 5. Type-safe context with immutable records

`RetryDecision`, `BackoffDelay`, and `DeadMessageContext` are all Java records with validation in compact constructors. No setters, no mutable state, no thread-safety concerns. Tests benefit from value equality and clear construction.

### 6. Self-describing `RetryDecision`

Carrying `maxAttempts` alongside `attempt` and `shouldRetry` makes each decision self-contained for logging, observability, and decision-auditing without requiring a back-reference to the originating policy. This was a solid trade-off over an enum-only representation.

## Risks

### R1: Sync/async code-path duplication in `DispatchOutboxMessageService` (Medium)

The `attemptDispatch` method has two near-identical retry paths:

- **Sync** (line 173–185): `catch (RuntimeException immediate)` — evaluates policy, schedules retry or fires handler + throws
- **Async** (line 187–198): `.exceptionallyCompose(pubEx → ...)` — evaluates policy, schedules retry or fires handler + fails future

The two paths share the same algorithm (evaluate → retry-or-stop) but are expressed as two separate code blocks with subtly different behaviors:

| Behavior | Sync path | Async path |
|----------|-----------|-----------|
| Policy evaluation | ✓ | ✓ |
| Backoff + schedule on RETRY | ✓ | ✓ |
| `markFailed` on STOP | ✓ (suppression) | ✓ (suppression) |
| Handler invocation | ✓ (fire-and-forget) | ✓ (awaited + absorbed) |
| Final failure propagation | `throw immediate` | `CompletableFuture.failedFuture(pubEx)` |

**Impact**: A bug fix or observability improvement to one path could be missed in the other. Future extensions (e.g., adding a metrics hook between policy evaluation and backoff) require changes in two places. This is an Open/Closed Principle concern — the dispatcher is not closed against extensions to the retry pipeline.

**Mitigation**: The tests cover both paths (immediate throw test and async failure test). The risk is about change-fragility, not current correctness.

### R2: Handler fire-and-forget inconsistency in sync STOP path (Low)

In the sync path (line 183–184):
```java
deadMessageHandler.handle(deadContext(message, attempt, immediate)); // fire-and-forget
throw immediate;
```

The handler's `CompletionStage<Void>` return is not awaited. If the handler does async I/O (e.g., writes to a Kafka DLQ), that work races with the thread's exit from `dispatch()`. In the async path, the handler is fully awaited before the stage completes exceptionally.

**Impact**: This is a contract inconsistency. A handler implementer reading the `DeadMessageHandler` interface sees `CompletionStage<Void>` (suggesting async is supported and observed), but the sync path ignores the return entirely. If a future handler makes async DLQ calls, the sync path provides weaker delivery guarantees than the async path.

**Mitigation**: The current `LoggingDeadMessageHandler` is synchronous (returns `completedFuture(null)`), so no data loss occurs today. The comment in the code ("fire-and-forget: the throw carries the primary signal; handler is a side-effect") documents the intent. This risk activates only when a non-logging handler is deployed.

### R3: Production dispatch runs without retry infrastructure (Medium)

`OutboxSchedulingAutoConfiguration:71-74` wires `DispatchOutboxMessageService` with the 2-arg constructor:
```java
@Bean
@ConditionalOnMissingBean
DispatchOutboxMessageService dispatchOutboxMessageService(
        final OutboundMessagePublisher publisher,
        final OutboxRepository outboxRepository) {
    return new DispatchOutboxMessageService(publisher, outboxRepository);
}
```

This creates a `SimpleRetryPolicy(1)` — no retry, no backoff, no `ScheduledRetryScheduler`, no `ExponentialBackoffStrategy`. The retry subsystem is implemented and tested but not wired into production. This is an intentional deferral (noted as a follow-up in the implementation reports), but it means the current production behavior is "one attempt, fail permanently" regardless of the subsystem's readiness.

**Impact**: Until auto-configuration is extended, transient Kafka failures will produce permanent dead messages with no retry attempt.

**Mitigation**: This is a configuration gap, not an architectural flaw. The report explicitly notes it as a follow-up.

### R4: `Instant.now()` bypasses `TimeProvider` in `deadContext()` (Low)

The dispatcher calls `Instant.now()` at line 212. Platform convention is to inject `TimeProvider` for reproducibility in tests. The implementation reports acknowledge this and argue that `failedAt` is diagnostic, not business-critical.

**Impact**: The `failedAt` field in `DeadMessageContext` cannot be frozen to a fixed time in unit tests. The current tests assert `isNotNull()` but cannot assert a specific value. This is acceptable for a diagnostic timestamp; it would matter only if the timestamp were used for ordering or replay logic.

## Improvement Opportunities

### I1: Unify the sync/async retry paths in the dispatcher (before Kafka integration)

The sync and async paths should share a single retry-or-stop decision pipeline. Extract the common logic to a private method:

```java
private CompletionStage<Void> handleRetryOrStop(
        OutboxEvent message, int attempt, Throwable failure) {
    RetryDecision decision = retryPolicy.evaluate(attempt, failure);
    if (decision.shouldRetry()) {
        int next = attempt + 1;
        BackoffDelay delay = backoffStrategy.nextDelay(next);
        return retryScheduler.schedule(() -> attemptDispatch(message, next), delay);
    }
    callMarkFailed(message, failure);
    return deadMessageHandler.handle(deadContext(message, attempt, failure))
            .handle((ignored, handlerEx) -> (Void) null)
            .thenCompose(ignored -> CompletableFuture.failedFuture(failure));
}
```

Then wire both paths through it:
- **Sync**: `try { publisher.publish(...) } catch (RuntimeException e) { return handleRetryOrStop(message, attempt, e); }`
- **Async**: `publisher.publish(...).exceptionallyCompose(pubEx -> handleRetryOrStop(message, attempt, pubEx))`

This eliminates the duplication, makes the sync path await the handler (resolving R2), and creates a single extension point for future pipeline steps.

### I2: Ship retry auto-configuration (before Kafka transport deployment)

Extend `OutboxSchedulingAutoConfiguration` with retry wiring:

```java
@Bean
@ConditionalOnMissingBean
RetryPolicy retryPolicy(OutboxPollingProperties props) {
    return new SimpleRetryPolicy(props.getRetryMaxAttempts());
}

@Bean
@ConditionalOnMissingBean
BackoffStrategy backoffStrategy(OutboxPollingProperties props) {
    return new ExponentialBackoffStrategy(
        Duration.ofMillis(props.getRetryInitialDelayMs()),
        props.getRetryMultiplier(),
        Duration.ofMillis(props.getRetryMaxDelayMs()));
}

@Bean
@ConditionalOnMissingBean
RetryScheduler retryScheduler(TaskScheduler taskScheduler) {
    return new ScheduledRetryScheduler(taskScheduler);
}

@Bean
@ConditionalOnMissingBean
DispatchOutboxMessageService dispatchOutboxMessageService(...) {
    return new DispatchOutboxMessageService(publisher, outboxRepository,
        retryPolicy, backoffStrategy, retryScheduler);
    // LoggingDeadMessageHandler is the default via the 5-arg constructor
}
```

This converts the retry subsystem from "implemented but dormant" to "implemented and active" without changing the subsystem itself. Configuration properties (`arbitrier.messaging.outbox.retry.*`) should default to reasonable values (maxAttempts=1, retaining current behavior as the safe default).

### I3: Add observability hooks to the retry pipeline (before production)

Each port should be observable without modifying the dispatcher. The cleanest approach: integrate with Resilience4j's `Retry`/`RetryRegistry` which already provides metrics (retry count, failure rate via Micrometer). This would replace `SimpleRetryPolicy` with a Resilience4j-backed `RetryPolicy` adapter without changing the dispatcher or the `RetryPolicy` interface.

If Resilience4j integration is deferred, at minimum add structured MDC logging at each pipeline step in the dispatcher — `attempt`, `decision`, `delay` — so operators can diagnose retry storms from logs.

### I4: Add jitter to `ExponentialBackoffStrategy` (before multi-worker deployment)

Multiple workers dispatching at the same cadence will synchronize their retry schedules, creating thundering-herd broker reconnection. Add a `JitteredBackoffStrategy` wrapper that decorates any `BackoffStrategy` by randomizing the computed delay within a configurable jitter factor (e.g., ±25%). This is a single new class — no changes to the dispatcher, scheduler, or existing strategy.

## Readiness Assessment

### Ready for Kafka integration — with minor improvements

The retry subsystem is well-designed at its four-port abstraction level. The contract boundaries are clear, the transport independence is genuine, and the `CompletionStage`-native design aligns with virtual-thread execution. Every port can be replaced independently, satisfying the Open/Closed Principle at the port boundary.

**Before Kafka transport is built on this foundation, implement I1 (unify sync/async paths) and I2 (ship auto-configuration).** These are not architectural redesigns — they are completion of the existing design's integration surface. I3 (observability) and I4 (jitter) should follow before multi-worker deployment but are not blockers for initial Kafka wiring.

**Rationale**: The question "Would you confidently build the Kafka transport layer on top of this retry infrastructure without redesigning it?" — yes, provided the sync/async path unification (I1) lands first, because the Kafka transport adapter will exercise both code paths and the current duplication creates a maintenance hazard.
