## Objective

Introduce runtime metrics for the outbox dispatch pipeline to provide quantitative operational visibility without modifying the retry infrastructure.

This slice complements the structured logging introduced in ARB-022.7.1.

## Context

The dispatcher is now capable of:

dispatching messages
retrying failed publications
scheduling retries
handling permanent failures

Operators should now be able to answer questions such as:

How many messages are dispatched?
How many retries occur?
How many messages ultimately fail?
What is the average dispatch latency?

## Scope
In Scope

Instrument the dispatcher using the platform's metrics abstraction (Micrometer if already adopted).

Capture at least:

Counters
messaging.dispatch.started
messaging.dispatch.succeeded
messaging.dispatch.failed
messaging.dispatch.retry
messaging.dispatch.dead
Timer
messaging.dispatch.duration

The timer should measure the complete dispatch lifecycle, including retries, until the operation reaches its final state.

## Metric Tags

Where applicable, include consistent tags such as:

aggregateType
eventType
outcome (success, failed, dead)
retry (true / false)

Avoid high-cardinality tags.

Do not tag with:

eventId
aggregateId
correlationId
requestId

## Out of Scope

Do not implement:

Prometheus dashboards
Grafana dashboards
OpenTelemetry metrics
tracing spans
alerting
custom exporters

This task only instruments the dispatcher.

## Acceptance Criteria
Dispatch lifecycle is measurable through counters and timers.
Retry attempts increment retry metrics.
Dead-message path increments dead-message metrics.
Success and failure paths are distinguished.
No behavioral changes.
Existing tests continue passing.
